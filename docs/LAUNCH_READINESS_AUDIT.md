## Evidence rules

- **Verified locally:** code path exists and relevant local checks passed. This does not imply a credentialed business journey passed.
- **Implemented, unverified:** code/database objects exist, but a real provider, browser, role, or warehouse journey has not been exercised.
- **Partial:** a necessary step, integration, UI, or durable transition is absent or known to fail.
- **Absent:** only mock/synthetic behavior or no implementation exists for the specified outcome.

The production build generated routes, and 256 web tests passed, but many tests inspect source text or pure functions. A route existing in the build is not proof that its database call, permission policy, external page adapter, or user flow succeeds.

## Database, authorization, and security

**Read-only connected-project findings:** the project reported `ACTIVE_HEALTHY`; its migration list includes local migrations through `20260911122533`. All 39 inspected `public` tables had RLS enabled. Private storage buckets `payment-proofs` (10 MB) and `cainiao-imports` (8 MB) exist with image/PDF and image-only MIME restrictions respectively. Storage object policies observed were for payment proofs; Cainiao evidence is uploaded through a server service-role path. These facts establish configuration, not end-to-end permission correctness.

1. **Favorites refresh is a confirmed permission mismatch.** `app/api/favorites/[id]/refresh/route.ts` uses the user-scoped Supabase client to select `client_favorites`; the connected database grants authenticated users neither SELECT nor INSERT on `client_favorites` or `favorite_refreshes`, and these tables have RLS enabled with zero policies. `GET /api/favorites` and the Favorites UI/estimate continuation specified in [the feature spec](./FEATURE_FAVORITES_REPEAT_ORDER.md) are absent. The current refresh route cannot work through that first read with the deployed grants. Favor an ownership-checked server/RPC path rather than broad table grants.
2. **Security advisor findings require triage.** The advisor reported an anonymously executable `public.rls_auto_enable()` SECURITY DEFINER function, seven SECURITY DEFINER functions executable by authenticated users (six client read/favorite RPCs plus `rls_auto_enable`), and leaked-password protection disabled. Inspection showed `rls_auto_enable()` returns `event_trigger` and is bound to DDL; its direct RPC exploitability was **not** tested. Review grants and function ownership checks, then run advisors again. SECURITY DEFINER is not itself proof of a vulnerability; the callable functions are a review queue.
3. **Three no-policy tables are intentionally closed to direct authenticated access, but must stay explicit.** `cainiao_import_batches`, `client_favorites`, and `favorite_refreshes` have RLS and zero policies; authenticated SELECT/INSERT grants were absent. The Cainiao import endpoints use a server service-role client after role authorization. Verify each privileged route derives actor/ownership on the server and that no new Data API exposure is accidentally granted.
4. **Service-role and extension boundary need dynamic testing.** Cainiao import/collection and product snapshot routes use `createSupabaseAdminClient()` after application authorization; extension credential wrappers impersonate the verified admin profile for RPCs. Inspect revocation, origin allowlist, wrapper grants, and cross-client/staff attempts in staging. Static tests alone do not prove RLS isolation.
5. **Dependencies need a release review.** `npm audit --omit=dev` on the root workspace reported 18 findings: 1 critical (`next`), 3 high (`js-yaml`, `postcss`, `sharp`), and 14 moderate. This is a dependency inventory, not an exploitability finding; reproduce it in December, assess affected paths/advisories, and update with regression coverage before launch.

## Specification and documentation conflicts

- The active direct multi-SKU confirmation path skips a persisted estimate/acceptance boundary required by the documented estimate workflow. The single-SKU estimate APIs remain; the product owner must approve the canonical user journey and API behavior before changing it.
- The [Favorites/Repeat spec](./FEATURE_FAVORITES_REPEAT_ORDER.md) requires a fresh snapshot, active list, and new estimate, while current route/API/UI coverage is incomplete and the first refresh read is denied.
- [Spec decisions](./SPEC_DECISIONS.md) still marks OC-003 (carton print transition), OC-005 (immutable snapshot revision strategy), OC-006 (split provider orders/tracking shape), and OC-007 (terminal record reopening) as owner decisions. Do not silently choose one while implementing dependent features.
- [Current implementation status](./CURRENT_IMPLEMENTATION_STATUS.md) is dated 2026-08-30 and understates auth, purchasing, and September logistics. [Frontend rebuild status](./FRONTEND_REBUILD_STATUS.md) says `npm test` is missing, but it now exists. [Client web status](./client-web/CLIENT_WEB_IMPLEMENTATION_STATUS.md) is dated 2026-09-02 and should be read as that phase's checkpoint, not a current launch verdict.
- `README.md` still describes an initial scaffold and a direct application of only `001_initial_schema.sql`; following that instruction alone would miss 72 later local migration files. Use the Supabase CLI migration workflow against an explicit safe target.
